# Name provenance

Every name in the 2nd Impact decompilation (function, global, type, enum, local) is a row in a table under
`ghidra/names/`, and the row says where the name came from. The model is the compiler rebuild's naming tables
(the compiler decomp's `ghidra/names/README.md`, gibletto/shc-5r26-decomp-sf3), with a provenance class and a 3rd Strike reference added to each row.

## Rules

- **The tables are the only source of names.** The Ghidra project (`ghidra/project/`, ignored) is generated by
  `tools/ghidra-import.sh` from the program image and `ghidra/scripts/SetupCps3.java`, and is never edited by hand.
  `tools/ghidra-export.sh` opens it read-only and applies the tables (`ghidra/scripts/ApplyTables.java`) in every
  session before it exports, so deleting the project and running both scripts again reproduces every name.
- **One name, one row.** A name is defined by exactly one row, together with its evidence. Renaming is editing that
  row; the next export shows the new name everywhere. `tools/check-tables.py` rejects duplicate names, duplicate
  addresses, unknown classes and rows missing the evidence their class requires.
- **Seeding never overwrites.** `tools/seed-tables.py` adds rows for addresses that have none and reports
  disagreements with existing rows; it does not change a row that is already there. Once a row has been edited by
  hand (with evidence), it belongs to that edit. Until then every row is the seeder's, and the tables may be
  regenerated from scratch when the seeder or its inputs improve; the commit says so.
- **No ROM content in the tables.** Rows hold addresses, names, classes, similarity figures and prose. They never
  hold bytes, hashes or disassembly copied from the image.

## Provenance classes

| Class | Meaning | Evidence required |
|---|---|---|
| `3s-exact` | byte-identical to the named 3s routine or object | `sf3_addr`, `sf3_name`; 3s and 2i bytes equal over the 3s size (a data object: its whole extent) |
| `3s-reloc` | identical apart from relocated addresses | as `3s-exact`, and the note gives the number of relocated words (`reloc 3`); every differing word is an address on both sides |
| `3s-near` | the same routine with changes | `sf3_addr`, `sf3_name`; the note starts `sim NN%` (aligned share of instruction words) and says what changed |
| `inferred` | named from context | the note gives the reason (callers, the data it reads, a debug string, a 3s analogue that is not the same routine) |
| `new` | a provisional name | none; replace it when something better is known |

For **RAM variables** there are no bytes to compare. The literal pools of the matched routines pair 3s addresses
with 2i ones (3s word -> 2i word, same pool slot), and each pair votes for the 3s symbol containing the 3s address.
A RAM global is `3s-exact` when the pairs keep its 3s address and `3s-reloc` when they move it; the note gives the
agreeing and conflicting references (`ram refs 12 conflicts 0`; a symbol needs two thirds of its votes). A RAM
global seen only from `3s-near` routines is `3s-near` with the same note. A **ROM data object** (a table) found
this way is compared byte for byte over its 3s extent: `3s-exact`, `3s-reloc` (`reloc N`), `3s-near` when at least
half its words are equal (`sim NN%`), else `inferred` (the name rests on the references alone). A pointer to a 3s
routine's entry names a 2i function the same way, as `inferred`.

**Identical copies and roles.** Some 3s routines exist byte for byte in several places (Yun's and Yang's
modules, the per-character AI stubs), so bytes alone do not say which 2i copy is which. The seeder places such a
routine by the other routines of its module, then by address order within a group of copies (the note says
`placed among the copies by address order`; the weakest placement). Pointers outrank both: where literal pools,
aligned ROM tables or si2map's table pins point a 3s routine's name at a 2i address, the routine goes there
(`placed by the pointers to it`). When the bytes there are another 3s routine's, the row is **named by its role
and classed by its bytes**: the name is the one the pointers give (the character-4 entry of a per-character table
is `Passive04`), while class, `sf3_addr`, `sf3_name` and `sf3_src` describe the 3s routine whose bytes it has
(`the bytes are sf3 Passive14, the name is its role here`). The C for it starts from that 3s source. A name that pointers
alone give (class `inferred`) yields to another 3s routine's exact or reloc bytes at that address: a 3s extent can
hold several static tables back to back, and a table word past the end of a shorter 2i table names the wrong slot
(the note says `replaces sf3 Passive02_0116, which only pointers put here`).

Classes rank `3s-exact` > `3s-reloc` > `3s-near` > `inferred` > `new`. A row moves up a rank only with the evidence
of the new class, and is demoted when its evidence fails (say, a 3s-near routine whose match turns out to be
another routine).

## The 3s reference

Three columns tie a row to 3rd Strike, which is the decompiled oracle (a built tree of gibletto/sfIII3-cps3-decomp):

- `sf3_addr`: the 3s arcade address (the key into `tmp/r50/ms34.tsv` and `sf3.map`), empty for `inferred`/`new`
  unless a 3s analogue is meant;
- `sf3_name`: the 3s name (normally the 2i name is the same; a different 2i name says why in the note);
- `sf3_src`: the 3s source location, `src/<module>:<line>` (or `include/<header>:<line>` for a type), relative to
  the 3s tree.

## Tables

All are tab-separated; `#` lines and blank lines are skipped. Columns beyond the compiler's are the provenance.

| File | Columns |
|---|---|
| `entries.tsv` | address, note: code the analysis leaves without a function (a dispatch-table target, a handler reached only through a pointer); seeds the import and is made a function in the export session |
| `functions.tsv` | address, name, signature, class, sf3_addr, sf3_name, sf3_src, note. A row also asserts a function entry: the import seeds it and the export session creates the function if the analysis did not |
| `globals.tsv` | address, name, type, class, sf3_addr, sf3_name, sf3_src, note |
| `types.h` | C struct/union definitions. `// @size NAME 0xNN` is checked against the parsed size; `// @prov NAME class sf3_src [note]` is the type's provenance (one per struct/union, checked by `check-tables.py`) |
| `enums.tsv` | enum, size, member, value, class, sf3_src. Class and source on an enum's first row, empty on the rest |
| `locals.tsv` | function, old name, new name, type, first use, storage, class, note |

Signatures, types, widths and the C-safety rules (no locals named like types, keywords or globals) follow the
compiler's `ghidra/names/README.md`.

## How the provenance shows up

`ApplyTables.java` sets each function and global row's provenance as the plate comment at its address
(`prov: 3s-exact sf3 task_sleep_tick@0600094C src/Entry.c:128 -- size 140`; the decompiler also prints it above the function). The export carries it: every
`decomp/<entry>_<name>.c` has a `// prov :` header line, and `functions.tsv` and `boundaries.tsv` a `prov` column.

## Feeding the C sources

- **Traceable by name.** Function and global names are unique, so a C function's provenance is the
  `functions.tsv` row with its name (and its address). The generated sources carry one comment line above each
  function, copied from the export header (`/* 2i 0600094C, 3s-exact: sf3 src/Entry.c:128 task_sleep_tick */`);
  it never affects code generation, and it is regenerated, not edited.
- **Where the C comes from.** For `3s-exact` and `3s-reloc` routines the starting C is the 3s source at `sf3_src`
  (the same compiler gives the same bytes; relocations come from the link). For `3s-near` it is the 3s source,
  edited by what the note says changed. `inferred` and `new` routines start from the Ghidra export.
- **A row outlives its seed.** When a routine's C is later written or matched by hand, the row stays the record of
  its name; the class keeps describing how the 2i binary relates to 3s, not how the C was written.

## The loop

```sh
S3=<dir>    # the 3s oracle: a built 3rd Strike tree at $S3/wt3/sf3 (sf3.map, verify/bootstrap/prog.bin) and its
            # routine table $S3/tmp/r50/ms34.tsv (match_status output of the 3rd Strike development tools)
M=scratch/si2map    # si2map (final): funcs.tsv, census.tsv (run with pins_merged.tsv), pins.tsv (its own table pins)
python tools/match3s_dual.py $S3/wt3/sf3/verify/bootstrap/prog.bin $S3/tmp/r50/ms34.tsv \
  scratch/rom/prog_op.bin scratch/rom/prog_data.bin scratch/si2ghidra/match_dual.tsv
python tools/seed-tables.py scratch/si2ghidra/match_dual.tsv $S3/wt3/sf3 $S3/wt3/sf3/verify/bootstrap/prog.bin \
  scratch/rom/prog_op.bin scratch/rom/prog_data.bin --pins $M/pins.tsv --census $M/census.tsv
python tools/check-tables.py                        # classes, evidence, duplicates, C-safe names
python tools/export-pins.py scratch/si2ghidra/pins_ghidra.tsv   # our pointer placements, for si2map's census pins
tools/ghidra-import.sh scratch/rom/prog.bin        # generated project; rerun when the tables gain seeds
tools/ghidra-export.sh --boundaries                 # read-only session with the tables applied
python tools/seed-entries.py $M/funcs.tsv scratch/si2ghidra/export/boundaries.tsv   # entries Ghidra misses
tools/ghidra-import.sh scratch/rom/prog.bin && tools/ghidra-export.sh    # again, with the entries; full export
python tools/compare-boundaries.py scratch/si2ghidra/export/boundaries.tsv $M
```
